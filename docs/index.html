Storage Strategy • Mobile Constraints

The Three Eviction Policies

Why unbounded caching breaks on mobile, and the trade-offs of each eviction strategy.

⚠️ Why Eviction is Mandatory
  • OS Low-Storage Purges: iOS and Android actively monitor app disk quotas. Apps that hog storage trigger OS prompts asking users to uninstall.
  • Query & Index Degradation: Unbounded local tables slow down queries like ORDER BY timeStamp DESC, increasing memory and query latency.
  • Stale Feed Decay: Feeds lose relevance quickly. Showing 3-week-old items as 'recent' degrades offline user experience.
⚖️ Policy Comparison
Policy Pros Mobile Drawback
TTL (Time-To-Live) Predictable freshness Doesn't stop rapid burst storage bloat
Count / Size Cap Guarantees hard DB bounds Needs sorting metric (FIFO vs Timestamp)
LRU (By View) Keeps favorite items Write-thrashing on scroll!

💡 Takeaway: Never use LRU on feed items—writing timestamps during scroll kills 60/120Hz frame rates. Use Timeline FIFO.

Architecture • Data Flow

Two-Tier Hybrid Eviction Architecture

Executing eviction at write-time so the launch read-path stays instant and 60fps smooth.

💡 Why Write-Time?
  • Zero UI Blocking: Launch read queries render instantly without delay. We never do heavy DB pruning during initial screen presentation.
  • Natural Boundary: We prune immediately upon adding fresh pages, keeping storage strictly bounded.
  • Background I/O: Executes on background coroutine/async workers, off the UI thread.
Database Deep Dive • SQLite Optimization

Indices, Cascades & Storage Reclamation

Optimizing SQLite execution plans and reclaiming physical disk space on mobile devices.

⚡ Indexing Strategy
-- Essential composite/single indices:
CREATE INDEX idx_posts_timestamp 
ON posts(timeStamp DESC);

CREATE INDEX idx_posts_cached_at 
ON posts(cachedAt);
  • Avoid Full Table Scans: Without an index on cachedAt, every write-time TTL check scans every row in SQLite!
  • Fast Feed Sorting: Indexing timeStamp DESC makes UI queries instantaneous.
  • Foreign Key Cascades: Declaring FOREIGN KEY (postId) REFERENCES posts(id) ON DELETE CASCADE cleans up child tables automatically.
🧹 Reclaiming Deleted Space
  • SQLite Free-Page Trap
    When you execute DELETE FROM posts, SQLite does not shrink the .db file on disk! It marks pages as 'free' for future writes.
  • PRAGMA auto_vacuum = INCREMENTAL
    Configuring incremental auto-vacuum allows your database to return freed storage pages back to the operating system during idle maintenance.
Media & Cache Bloat • The Blob Gap

The Physical Disk Gap: Metadata vs. Media

Why evicting a database row doesn't clean up the images and videos taking up real disk space.

📦 The Two Storage Layers
  • Structured Metadata (SQLite / Drift):
    Stores text, IDs, timestamps, and image URLs. Usually takes a few megabytes (~10–20MB for hundreds of posts).
  • Binary Media Blobs (Disk Cache):
    Stored in cacheDir by image loaders (Coil, CachedNetworkImage, FastImage). This is what consumes 500MB–2GB of disk!

⚠️ Deleting a database row leaves the downloaded image blob orphaned in the disk cache!

🛠️ Two-Tier Media Eviction Solution
  • 1. Image Loader DiskLruCache
    Configure strict byte-size caps on Coil / Dio Cache / FastImage (e.g. maxSize(150.MB)). The image loader handles LRU blob eviction automatically.
  • 2. Background Idle Cleanup (WorkManager / BGTask)
    Schedule periodic maintenance running only when:
    • requiresDeviceIdle()
    • requiresCharging()
    Cleans temp files, video chunks, and orphan assets without draining battery.
The Hidden Bug • Time Integrity

The "Lying Device Clock" Dilemma

Why device wall-clock time (Date.now() / DateTime.now()) is dangerous for cache eviction.

💥 Failure Scenario

Suppose cache TTL is 1 hour. What happens if:

  • User travels or sets clock 1 day ahead: Wall clock jumps +24h. The next eviction query deletes 100% of cached posts. Offline mode is wiped!
  • User sets clock back: Cached items are marked in the past; stale posts never expire, consuming disk indefinitely.
  • Ranked feed returns older post: If we mistakenly used serverCreatedAt instead of cache arrival time, the post is deleted on insertion!
🛣️ Real-World Analogies
  • The Unix Epoch = KM 0 Stone
    Just like National Highways start at KM 0 at the city center, Epoch (Jan 1, 1970 UTC) is the KM 0 of computing. Timestamps are simply the kilometer reading.
  • Monotonic Clock = Bike Odometer
    When a brand new bike leaves the factory, its odometer starts at 0. You cannot fast-forward it in Settings; it only counts forward at a steady, reliable pace.
Deep Dive • Mobile OS Internals

The Two Clocks in Mobile

Bridging device hardware boot stopwatches with universal UTC time.

📐 The Clock Skew Formula

We store a single thread-safe offset:

// 1. On server response:
val skew = serverUtc - monotonicClock

// 2. Anytime we need "Now":
fun now() = monotonicClock + skew
  • Tamper-Proof: User changing system clock by 5 years does not change monotonic time.
  • Zero Drift: Advances with hardware crystal precision.
Implementation • Clean Architecture

Piggyback Time Sync via HTTP Interceptor

Zero dedicated NTP requests. Zero battery drain. Free time sync with every API response.

1 HTTP Interceptor Pattern
// Works in OkHttp / Dio / Axios
fun onResponse(response: Response) {
    val serverDate = response.headers["Date"]
    if (serverDate != null) {
        timeProvider.updateServerTime(
            parseDate(serverDate).time
        )
    }
}

Runs transparently on every network request your app already makes.

2 Repository Usage
class FeedRepository(
    private val localDb: PostDao,
    private val api: FeedApiService,
    private val timeProvider: TimeProvider
) {
    suspend fun refreshFeed() {
        val now = timeProvider.currentTimeMillis()
        localDb.insert(posts, cachedAt = now)
        localDb.deleteOlderThan(now - CACHE_EXPIRY)
    }
}
Distributed Systems • Offline Mutations

Offline Mutations, Idempotency & LWW

How tamper-proof time powers Last-Write-Wins (LWW) and eliminates duplicate mutation retries.

🔑 Idempotency via Snowflake requestId

Mobile connections drop mid-flight. When the client retries, how does the server know it's not a duplicate?

// Snowflake ID = [41-bit Timestamp] + [10-bit Device ID] + [12-bit Sequence]
data class PostInteractionRequest(
    val requestId: String, // Idempotency Key
    val action: String     // "LIKE", "UNLIKE"
)
  • Safe Retries: If the network drops before receiving the response, retrying with the same requestId guarantees the server executes the mutation exactly once.
⚔️ Conflict Resolution: Last-Write-Wins
  • The Multi-Device Race
    User unlikes a post on Device A (offline), then likes on Device B (online). Device A reconnects 10 minutes later. Which write wins?
  • Why Time Synchronization is Crucial
    In a Last-Write-Wins (LWW) system, the server accepts the mutation with the highest timestamp. If Device A had a tampered wall clock (set to 2030), its stale offline unlike would overwrite Device B forever! Server-synced monotonic time prevents this catastrophic conflict.
Summary • Rules of Thumb

Key Takeaways for Developers

Four production rules of thumb to apply across mobile applications.

1
Enforce Two-Tier Hybrid Eviction

Run TTL first to discard stale items, then apply a hard count-cap to bound local database size. Trigger at write-time so app launch reads stay instant.

2
Avoid LRU in Scrolling Feeds

Updating view timestamps during scroll causes disk thrashing and dropped UI frames. Use FIFO timeline ordering instead.

3
Never Trust Wall Clock for Local State

Pair hardware monotonic stopwatches with HTTP Date headers to eliminate clock skew and time tampering.

4
Use Snowflake Idempotency for Offline Writes

Tag mutations with client-generated requestIds so network retries never produce duplicate likes or posts.
